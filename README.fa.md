# تمرین استخدامی: همگام‌سازی حسابداری و داشبورد

قرار است یک ابزار داخلی بسازید که داده‌های یک سرویس حسابداری شخص ثالث را در سیستم خود کپی و
همگام نگه می‌دارد و آن‌ها را در اختیار تیم مالی قرار می‌دهد.

زیرساخت پروژه از قبل آماده شده است. بخش‌های اصلی و جذاب کار — همگام‌سازی، داشبورد و یک قابلیت
CRUD — هنوز پیاده‌سازی نشده‌اند. تمرین شما همین است.

**محدودیت زمانی: دو روز؛ و واقعاً منظورمان همین است.** انتظار ما حدود ۶ تا ۸ ساعت کار متمرکز است،
نه تمام آخر هفته. اگر زمان کم آوردید، کار را متوقف کنید و در `NOTES.md` بنویسید در ادامه چه
کارهایی انجام می‌دادید. یک توضیح صادقانه مثل «اینجا متوقف شدم و دلیلش این بود» بهتر از یک قابلیت
نیمه‌کاره و عجولانه است.

بعد از تحویل، با هم کد را مرور خواهیم کرد. انتظار داشته باشید دربارهٔ *چرایی* تصمیم‌ها از شما سؤال
شود؛ بنابراین هر جا تصمیمی بر اساس قضاوت خودتان گرفته‌اید، آمادهٔ دفاع از آن باشید.

## امکاناتی که از قبل در اختیارتان قرار گرفته است

| بخش | محل | وضعیت |
| --- | --- | --- |
| API شبیه‌سازی‌شدهٔ سرویس حسابداری خارجی | `mock-service/` (FastAPI، پورت 8001) | تکمیل شده است. **آن را تغییر ندهید.** |
| پروژهٔ Django + DRF | `backend/` (پورت 8000) | پیکربندی شده؛ منطق اپلیکیشن به‌صورت stub است |
| Celery worker و beat متصل به RabbitMQ | `docker-compose.yml` | در حال اجرا؛ هنوز taskای نوشته نشده است |
| PostgreSQL | `docker-compose.yml` (پورت 5432) | در حال اجرا |
| فرانت‌اند React + TypeScript | `frontend/` (Vite، پورت 5173) | اسکلت اولیه همراه با یک قابلیت نمونه آماده است |

احراز هویت و مدیریت کاربران **خارج از محدودهٔ این تمرین** هستند. قابلیت ورود، نقش‌ها یا مجوزها را
پیاده‌سازی نکنید. اگر می‌خواهید داده‌های دیتابیس را بررسی کنید، در Django admin یک superuser با
نام کاربری `admin` و رمز عبور `admin` از قبل ساخته شده است.

## راه‌اندازی

```bash
# بک‌اند، worker، beat، PostgreSQL، RabbitMQ و سرویس شبیه‌سازی‌شده
docker compose up --build

# فرانت‌اند (خارج از Docker)
cd frontend
npm install
npm run dev
```

سپس سرویس‌ها از نشانی‌های زیر در دسترس خواهند بود:

- اپلیکیشن: http://localhost:5173
- API: http://localhost:8000/api/health/
- Django admin: http://localhost:8000/admin/ (`admin` / `admin`)
- مستندات API سرویس حسابداری شبیه‌سازی‌شده: http://localhost:8001/docs
- رابط مدیریتی RabbitMQ: http://localhost:15672 (`guest` / `guest`)

دستورهای کاربردی:

```bash
docker compose exec backend python manage.py makemigrations
docker compose exec backend python manage.py migrate
docker compose exec backend pytest
docker compose logs -f worker beat
```

## سرویس خارجی

نشانی پایه در محیط Compose برابر `http://mock-accounting:8001` است (از روی سیستم میزبان:
`http://localhost:8001`). برای احراز هویت از هدر `X-API-Key: dev-secret-key` استفاده می‌شود.
هر دو مقدار از قبل در تنظیمات Django با نام‌های `EXTERNAL_ACCOUNTING_BASE_URL` و
`EXTERNAL_ACCOUNTING_API_KEY` تعریف شده‌اند.

```text
GET /api/v1/invoices?page=1&page_size=50&updated_since=2026-01-01T00:00:00Z
GET /api/v1/transactions?page=1&page_size=50&updated_since=...
```

پاسخ:

```json
{
  "items": [ ... ],
  "page": 1,
  "page_size": 50,
  "total": 240,
  "next_page": 2
}
```

نکات مهم زیر دربارهٔ این سرویس همگی عمدی هستند:

- حداکثر مقدار `page_size` برابر **۱۰۰** است؛ درخواست مقدار بیشتر با پاسخ 422 مواجه می‌شود.
- نتایج بر اساس `updated_at` به‌صورت صعودی مرتب می‌شوند.
- فیلتر `updated_since` **شامل مقدار مرزی** است (`updated_at >= value`)؛ بنابراین در هر اجرای
  incremental، برخی رکوردهایی را که از قبل دارید دوباره دریافت خواهید کرد.
- مبالغ به شکل **رشته‌های اعشاری** مانند `"1204.50"` ارسال می‌شوند و ارز invoiceها USD، EUR یا
  GBP است.
- سرویس گاهی شکست می‌خورد. حدود ۱۵٪ درخواست‌های داده پاسخ 500، 502 یا 503 می‌گیرند، حدود ۱۰٪
  درخواست‌ها ۳ تا ۸ ثانیه طول می‌کشند و محدودیت نرخ درخواست برابر ۱۲۰ درخواست در دقیقه است که در
  صورت عبور از آن، پاسخ 429 به‌همراه هدر `Retry-After` برمی‌گردد.
- مجموعه‌دادهٔ upstream به‌مرور **تغییر می‌کند**: هر ۶۰ ثانیه وضعیت تعدادی invoice تغییر می‌کند یا
  پرداخت می‌شوند و invoiceهای جدیدی نیز اضافه می‌شوند. فراخوانی `POST /admin/drift` این تغییر را
  فوراً اعمال می‌کند و سریع‌ترین راه برای آزمایش incremental sync بدون منتظر ماندن است.
- ممکن است یک transaction به invoiceای اشاره کند که هنوز آن را ذخیره نکرده‌اید.

هنگام توسعه می‌توانید مقادیر `FAILURE_RATE` و `SLOW_RATE` را در `docker-compose.yml` کاهش دهید.
پیش از تحویل، آن‌ها را به مقادیر پیش‌فرض برگردانید؛ ارزیابی پروژه با مقادیر پیش‌فرض انجام می‌شود.

## تسک ۱ — فرایند همگام‌سازی (بخش اصلی تمرین)

با استفاده از یک Celery task، invoiceها و transactionها را در PostgreSQL کپی و همگام کنید.

**الزامات:**

1. همگام‌سازی باید با Celery beat به‌طور خودکار **هر ۳۰ دقیقه** اجرا شود و امکان اجرای دستی آن از
   داشبورد نیز وجود داشته باشد.
2. صفحه‌بندی کل مجموعه‌داده باید مدیریت شود.
3. عملیات باید **idempotent** باشد؛ اجرای دوبارهٔ آن نباید دادهٔ تکراری ایجاد کند یا داده‌ها را
   خراب کند.
4. باید در برابر مشکلات سرویس خارجی مقاوم باشد: retry با backoff داشته باشد، در پاسخ 429 به
   `Retry-After` احترام بگذارد، روی پاسخ‌های کند برای همیشه معطل نشود و به‌دلیل شکست یک درخواست،
   صفحه‌ای از داده‌ها را از دست ندهد.
5. دو فرایند همگام‌سازی نباید هم‌زمان روی هم اجرا شوند.
6. اطلاعات هر اجرا ثبت شود: زمان اجرا، مدت، نتیجه، موارد تغییرکرده و خطاهای رخ‌داده؛ تا داشبورد
   بتواند سلامت همگام‌سازی را گزارش کند.
7. پس از اجرای اول، همگام‌سازی‌ها باید incremental باشند. اسکن کامل داده‌ها هر ۳۰ دقیقه قابل قبول
   نیست. همچنین watermark کردن با فیلتری که مقدار مرزی را شامل می‌شود، حالت خاصی دارد که باید به
   آن فکر کنید.

طراحی schema بر عهدهٔ شماست؛ فایل `backend/apps/accounting/models.py` عمداً خالی گذاشته شده است.

**مایلیم برای این بخش تست ببینیم**؛ حداقل این موارد را پوشش دهید: اجرای دوم هیچ تغییری ایجاد نکند
و شکست در میانهٔ صفحه‌بندی، دیتابیس را در وضعیت سالم نگه دارد. کتابخانهٔ `responses` برای شبیه‌سازی
سرویس خارجی نصب شده است.

## تسک ۲ — داشبورد

یک صفحه در اپلیکیشن React بسازید که موارد زیر را نمایش دهد:

1. اعداد خلاصه: تعداد کل invoiceها، مجموع مبالغ پرداخت‌نشده و مبلغ وصول‌شده در ماه جاری.
2. یک نمودار با `@mui/x-charts`؛ می‌توانید invoiceها را بر اساس وضعیت یا مبالغ وصول‌شده را در طول
   زمان نمایش دهید.
3. سلامت همگام‌سازی: آخرین همگام‌سازی چه زمانی اجرا شده، آیا موفق بوده و چند رکورد را تغییر داده
   است.
4. یک دکمهٔ **Sync now** که task را در صف قرار دهد، بلافاصله بازخورد بدهد و پس از پایان، نتیجه را
   نمایش دهد. استفاده از polling قابل قبول است و نیازی به WebSocket نیست.

عملیات aggregation باید **در دیتابیس** انجام شود. اگر برای جمع کردن مبالغ در Python روی QuerySet
حلقه می‌زنید، کار را متوقف کنید و روش را تغییر دهید.

مدیریت ارزهای مختلف بر عهدهٔ شماست. هر راه‌حل قابل دفاعی پذیرفته است؛ می‌توانید مجموع هر ارز را
جداگانه نمایش دهید یا یک ارز را انتخاب و آن را به‌وضوح برچسب‌گذاری کنید، به شرط آنکه عدد نمایش‌داده‌شده
بی‌سروصدا نادرست نباشد.

## تسک ۳ — تعدیلات دستی (فرم و جدول)

تیم مالی باید بتواند اصلاحاتی را برای invoiceهای همگام‌شده ثبت کند؛ برای مثال حذف یک طلب
(write-off)، کارمزد مورد اختلاف یا تفاوت ناشی از تبدیل ارز.

**بک‌اند:** یک CRUD با DRF برای adjustment پیاده‌سازی کنید که حداقل شامل مرجع invoice، مبلغ، دلیل
و زمان‌های ایجاد و به‌روزرسانی باشد. اعتبارسنجی واقعی همراه با خطاهای مختص هر فیلد لازم است. endpoint
لیست باید صفحه‌بندی‌شده و قابل فیلتر یا جست‌وجو باشد.

**فرانت‌اند:** یک فرم مبتنی بر `react-hook-form` و `yup` برای ایجاد و ویرایش بسازید و جدولی با
`@mui/x-data-grid` پیاده‌سازی کنید که صفحه‌بندی سمت سرور، فیلتر، ویرایش و حذف داشته باشد. خطاهای
اعتبارسنجی سمت سرور باید روی فیلد مربوط به خود نمایش داده شوند.

Adjustmentها متعلق به سیستم ما هستند، نه سرویس خارجی؛ فرایند همگام‌سازی هرگز نباید آن‌ها را
بازنویسی یا حذف کند.

## قوانین کلی

- فناوری‌ها ثابت هستند: در بک‌اند Django، DRF، Celery، RabbitMQ و PostgreSQL و در فرانت‌اند React،
  TypeScript، MUI، TanStack Query، react-hook-form و yup. فایل `frontend/AGENTS.md` را ببینید؛
  قراردادهای فرانت‌اند الزام هستند، نه پیشنهاد.
- استفاده از هوش مصنوعی مجاز و مورد انتظار است. در عین حال انتظار می‌رود تمام خطوطی را که تحویل
  می‌دهید، درک کنید.
- برای این موارد وقت صرف نکنید: احراز هویت، استقرار، CI، پرداخت بصری بیشتر از حد «مرتب و خوانا»،
  اجرای فرانت‌اند در Docker یا پوشش تست ۱۰۰٪.

## معیارهای ارزیابی ما

صحت فرایند همگام‌سازی در شرایط شکست و اجرای تکراری؛ schema متناسب با دامنه؛ queryهای مقیاس‌پذیر؛
طراحی منطقی API؛ فرانت‌اندی که قراردادهای پروژه را رعایت کند و حالت‌های loading، error و empty را
مدیریت کند؛ و استدلال شفاف.

## نحوهٔ تحویل

یک repository گیت (یا فایل zip) همراه با تاریخچهٔ commitها و یک فایل `NOTES.md` که موارد زیر را
پوشش دهد:

- روش اجرای هر چیزی که صرفاً با `docker compose up` اجرا نمی‌شود.
- تصمیم‌هایی که می‌خواهید از آن‌ها دفاع کنید و trade-offهای پشت آن‌ها.
- کارهایی که اگر یک هفتهٔ دیگر زمان داشتید انجام می‌دادید.
- هر مورد خراب یا ناتمامی که آگاهانه باقی گذاشته‌اید.
